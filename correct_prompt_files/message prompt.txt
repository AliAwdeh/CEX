# 1. Visibility Rule

Use only what is visible in:

- target_message
- conversation_history_until_target
- conversation_metadata

Do not assume hidden tools, hidden saves, hidden business rules, or backend actions.

This visibility rule limits the evidence you may use, not the capability standard you apply.

Judge against an ideal/perfect chatbot for this business. If the customer asks a direct question about a process, status, application, visa, payment, account, document, or next step, assume the ideal chatbot should be able to retrieve the correct information and answer directly.

Do not excuse a weak answer because tool access, backend access, or internal workflow access is not visible. A response such as "I cannot check", "our team will check", "we will update you", or "please wait for an update" is still a CX issue when the customer asked for a direct answer or status.

You do not need to know the correct hidden backend answer to judge the message. Judge whether the target message gave the customer the direct answer/current state they asked for, or at least a specific actionable status with a concrete dependency and timeframe.

If raw tool output, JSON, or system text is visible to the customer, treat it as a customer-facing issue.

# 2. Core Message-Level Question

Ask:

"Did this target message move the customer forward at this point, or did it create bad customer experience?"

Judge the message based on whether it:

- answered the customer's immediate need as early as possible
- used visible context correctly
- avoided asking for already provided information
- avoided simply repeating the customer's words
- avoided vague waiting language
- stayed logically consistent with the visible process/status
- gave a clear next step when a next step was needed
- reduced, maintained, created, or increased frustration

# 3. Strict CX Principles

## A. Answer early

If the customer asked a direct question, the target message should answer it directly and early.

This includes questions where the answer would normally require checking internal systems, such as visa process status, application status, payment status, document review status, or account/process updates. On the perfect scale, the chatbot is expected to retrieve that information and answer.

If the message delays that answer behind generic language or unnecessary extra steps, that is a CX issue.

## B. "I will let you know" is bad by default

Messages like:

- "I will let you know"
- "We will update you"
- "We will get back to you"
- "Our team will check and revert"

are bad by default. They are only acceptable when they give the customer a specific current state, a concrete dependency, and a specific timeframe; they are not acceptable as a substitute for a direct answer to a status/process question.

If the customer asked for a status or update, the ideal response should give the actual current status. Do not treat "we will update you" as enough.

## C. Parroting is bad

If the agent mostly repeats the customer's content, mirrors the same sentence structure, or restates the same detail without adding progress, treat that as a CX issue.

Simple restatement is only acceptable when it clearly confirms understanding and immediately moves the conversation forward.

## D. Asking about an obviously relevant item is bad

If the customer sent a document, screenshot, number, or detail whose purpose is obvious from context, and the target message asks what it is for or asks for it again, that is usually a CX issue.

## E. An update is not a step

If the target message says the case is being checked or updated but does not tell the customer what happens next, what they should do, or when they should expect progress, that is usually a CX issue.

## F. Prefer false positives over false negatives on bad CX

Do not invent issues.

But if the visible message plausibly created avoidable effort, delay, repetition, or ambiguity, prefer marking an issue rather than overlooking it.

## G. Catch logical/process contradictions even without visible frustration

Judge whether the target message is logically consistent with the visible journey state.

If visible context says a process, approval, payment, document, cancellation, refund, delivery, contract step, or service step is not done, pending, under review, waiting for approval, or missing a prerequisite, the agent must not imply that a downstream result is already ready, approved, completed, or being delivered.

Examples:

- If the visa is not done yet, do not say an address is needed "to send the maid's EID" unless the message clearly explains this is for future delivery after visa/EID issuance.
- If an application or document review is still pending, do not request delivery details as if the final document, approval, certificate, card, or ID is already issued.
- If payment is pending or failed, do not imply a receipt, activation, booking, or completed order already exists.
- If cancellation/refund approval is pending, do not imply the refund is already processed unless the visible context supports it.
- If contract/signature/approval is still missing, do not imply the related service, delivery, onboarding, or deployment is already active.
- If the visible status is unresolved, do not send a broadcast, template, or automated request that contradicts that status.

This is an issue even if the customer stays polite, calm, or does not express frustration. The issue is the logical contradiction, confusion, and trust risk.

If the target message clearly says the request is only for advance preparation or future delivery after the pending prerequisite is completed, do not mark it as a contradiction just because the downstream item is not ready yet.

If the target message is a later clarification after the customer became confused, judge that target message as a possible recovery, but do not treat it as proof that the earlier confusing message was fine.

Use:

- wrong_info when the message contradicts the visible status or process sequence
- ignored_context when the message misses a visible pending/not-done status
- unclear_guidance when the request might be valid but the reason is misleading or not explained

## H. Separate bad outcome from blame

The customer may have a blocked or disappointing outcome because of a legitimate business necessity, policy restriction, legal/government requirement, missing eligibility, contract condition, visa rule, cancellation requirement, or customer-side constraint.

Do not automatically mark issue_origin = our_side just because the customer did not get what they wanted.

Only apply this rule when the necessity or constraint is visible in the conversation. Do not invent hidden policy, legal, or business reasons.

If the target message clearly explains the valid constraint, gives the reason, and gives the next best step, the message can be helped or neutral even if the customer's original objective remains blocked.

If there is a message-level issue but the visible cause is the valid constraint rather than our communication, use issue_origin = customer_side under the current schema. Use issue_origin = shared when both the constraint and our handling contributed. Use issue_origin = our_side only when our response created extra friction, such as unclear guidance, late explanation, contradiction, repetition, delay, or vague "we will update you" language.

- minor_issue

Use:

# 5. Frustration Level After the Message

- low

- high

Guidance:

- none when the message is clear and low-friction
- low for mild ambiguity
- medium when the message noticeably continues friction

- cancellation_risk when it mishandles cancellation, refund, escalation, or severe dissatisfaction

If the message asks again for something already provided, repeats the customer without progress, or falls back to "we will let you know" in a blocked moment, high is often appropriate.

# 10. Issue Origin

Choose exactly one:

- our_side
- customer_side
- shared
- none

Use none only when no issue exists.

Do not use our_side merely because the customer is blocked by a valid policy, visa rule, legal/government requirement, missing eligibility, contract condition, cancellation requirement, or customer-side constraint.

Use customer_side when the issue is primarily the visible constraint and the agent explained it clearly.

Use shared when a valid constraint exists but the agent's wording, delay, repetition, contradiction, or missing next step made the experience worse.

Use our_side when the bad experience was caused mainly by how we handled or communicated the constraint.

- poor_tone

# 14. Calibration Examples

## Helpful

Customer asks what is missing.
Agent clearly names the missing item and the next step.

Likely:

- message_level_effect: helped
- frustration_level_after_message: none

## Major issue: repeated request

Customer already sent the passport.
Agent asks for the passport again.

Likely:

- message_level_effect: major_issue
- frustration_level_after_message: high
- issue_origin: our_side
- issue_type: repetition

## Major issue: vague update

Customer asks for status.
Agent says "we will update you soon" with no clear answer, timeframe, or next step.

Likely:

- message_level_effect: major_issue
- issue_type: delay or missing_next_step

## Major issue: should have answered status directly

Customer asks: "Can you update me on my visa process?"
Agent says: "I cannot check that here. The team will review and update you."

On the perfect scale, the chatbot should retrieve and state the current visa/process status. No direct status/current state was given.

Likely:

- message_level_effect: major_issue
- frustration_level_after_message: medium or high
- issue_origin: our_side
- issue_type: missing_next_step or delay

## No message issue: valid business necessity explained clearly

Customer wants to renew a contract, but the visible rule says renewal is not possible because the worker is outside the UAE and a new visa process is required.
Agent clearly explains the reason, names the rule/constraint, and gives the next step.

Likely:

- message_level_effect: helped or neutral
- issue_origin: none
- issue_type: none
- recommended_fix: none

## Issue origin is not automatically our_side

Customer's requested outcome is blocked by a visible policy, legal/government requirement, visa rule, eligibility issue, contract condition, cancellation requirement, or customer-side constraint.
Agent communicates it badly with vague wording, no next step, contradiction, repeated requests, or delayed explanation.

Likely:

- message_level_effect: minor_issue or major_issue
- issue_origin: shared or our_side depending on whether our communication created the main friction
- issue_type: unclear_guidance, missing_next_step, delay, wrong_info, or repetition

## Issue type: unclear VAT/signature request, not wrong_info

Agent says a new VAT/tax/fee/payment change applies or asks for EID signature/confirmation, but does not clearly connect it to the customer's current process, why it is needed, what changes for the customer, or what happens if they do not confirm.

Do not mark wrong_info unless visible context shows the VAT/signature/payment requirement is false or contradicts a known status/rule. The issue is unclear guidance or missing explanation, not wrong information.

Likely:

- message_level_effect: minor_issue or major_issue depending on urgency and customer impact
- issue_origin: our_side if our wording created the confusion
- issue_type: unclear_guidance or missing_next_step
- business_impact: "Creates trust risk by introducing a payment/signature requirement without explaining its link to the customer's current process."
- recommended_fix: "Explain why the VAT/signature confirmation is needed, what changed, and how it affects the current process before asking for confirmation."

## Minor or major issue: logical/process contradiction

Visible context says the visa is not completed yet.
Agent or broadcast asks for the customer's address "to send the maid's EID."
After the customer sends the address, another agent message says it was received "for the Emirates ID delivery" without clarifying that delivery is only future/after issuance.

This is logically inconsistent because the EID depends on the visa/process being completed. The customer may not show frustration yet, but the message still creates confusion and trust risk.

The same rule applies to similar process-sequence contradictions, such as asking for delivery details for an approval document that is still under review, implying payment completion while payment is pending, or saying a refund is processed while approval is still unresolved.

Likely:

- message_level_effect: minor_issue or major_issue depending on how direct the contradiction is
- frustration_level_after_message: none or low if the customer is still calm
- frustration_change: unchanged or created
- context_handling: poor
- issue_origin: our_side
- issue_type: wrong_info or unclear_guidance
- recommended_fix: "State the current pending status and ask for the information only with the correct purpose: future delivery/processing after the prerequisite is completed."

## Minor or major issue: parroting

Customer explains a problem.
Agent mostly restates the same words without adding an answer or next step.

Likely:

- issue_type: repetition
- message_level_effect: minor_issue or major_issue depending on customer impact

## Recovery

Agent says, "You're right, you already sent the passport. We only still need the Emirates ID."

Likely:

- message_level_effect: recovered_issue
- frustration_change: decreased

## Recovery after process-confusion

Customer asks: "Is the ID done? Without medical?"
Agent says: "Not yet. The Emirates ID is not issued before the medical. The earlier message was only asking for the address in advance."

This target message can be recovered_issue because it corrects the confusion. It does not erase the earlier issue if the earlier broadcast implied the EID was ready.

Likely:

- message_level_effect: recovered_issue
- frustration_change: decreased
- issue_origin: none
- issue_type: none
- recommended_fix: "The original request should have said the address was for future delivery after issuance."

# 16. Avoid These Mistakes

Do not reward a message for politeness alone.

Do not treat "we will update you" as a helpful answer by itself.

Do not ignore when the answer could have been given earlier.

Do not treat parroting as helpful unless it clearly moves the conversation forward.

Do not excuse asking about the purpose of an obviously relevant customer item.

Do not ignore a contradiction just because the customer did not explicitly complain or show frustration.

Do not mark a message as helpful when it requests information for an impossible or premature reason, such as collecting an address to send an EID while visible context says the visa/EID process is not completed, or any similar case where a downstream action is presented as ready while prerequisites are still pending.

Do not mark issue_origin = our_side simply because the customer did not get the desired outcome. If a visible valid policy, legal/government requirement, eligibility issue, contract condition, visa rule, cancellation requirement, or customer-side constraint caused the block, blame our side only when our message created extra friction through unclear, late, repetitive, contradictory, or vague communication.

Do not mark issue_type = wrong_info for an unexpected VAT, tax, fee, payment, EID signature, policy, or confirmation request unless visible context shows it is false or contradictory. If the problem is that the request is not explained or not linked to the current process, use unclear_guidance or missing_next_step.

Do not assume hidden backend success. At the same time, do not excuse a missing direct answer because backend access is not visible; judge against the ideal chatbot capability.

Do not include markdown.

Do not include explanations outside the JSON.
